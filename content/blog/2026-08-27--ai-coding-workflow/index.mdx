最近准备在团队内部做一次 AI Coding 分享。

一开始我只打算整理一下自己现在用哪些工具、平时怎么让 Agent 写代码。真正开始写以后，内容很快失控了：工具只是最外面一层，后面还有 Context、Skills、Runtime、Artifact、验证、多 Agent 和 Automation。原本的一篇文章越写越长，最后干脆拆成了四篇。

这次整理也正好逼着我回头看了一遍自己的变化。早期用 AI，更多是问 API、解释报错、补一段代码；现在则经常把完整任务交给 Coding Agent，让它读仓库、查调用关系、修改代码、跑测试、看浏览器或真机结果，再根据证据继续推进。

任务变长以后，关注点也跟着变了。模型会不会写代码当然还重要，但日常更容易出问题的地方，往往是上下文给错了、工具拿不到真实状态、长任务无法恢复、Skill 用得过头，或者 Agent 自己说“完成了”，却没有足够证据证明真的完成。

所以这次分享想讲的，其实是我现在怎么处理这些问题。

这套东西只是我当前个人开发环境的一张快照，不是团队规范，也不准备包装成一套标准流程。模型、Coding Agent 和 Runtime 还在快速变化，具体工具以后肯定会换；我更想留下的是那些在真实项目里反复出现的问题，以及目前对我有效的处理方式。

## 一：我现在实际在用哪些工具

[工具篇](/ai-coding-workflow-1/) 先从最外层讲起。

里面记录了我现在常用的 ChatGPT / Codex、Pi、CodeGraph、Context7、Chrome DevTools MCP、终端工具，以及哪些重复工作已经交给 Automation。

这一篇比较接近日常工作台：什么能力值得长期保留，什么工具只在特定场景使用，以及我为什么越来越在意“能不能拿到真实工程状态”，而不是单纯比较哪个 Agent 功能更多。

## 二：Engineering Skills 怎么进入日常开发

[Skills 日常工作流篇](/ai-coding-workflow-2/) 是这次改动最大的一篇。

我以前很容易把 Skill 设计成一条完整流水线，`wayfinding -> grilling -> to-spec -> implement -> simplify -> code-review` 一路走到底。真实项目里用久以后，这种设计越来越别扭：一个很小的修改也被迫走流程，需求已经清楚还要重新探索，Runtime 已经有 Goal 和 resume，Skill 又套一层自己的生命周期。

现在我更倾向于先判断当前还缺什么，再选负责这个阶段的 Workflow；`debug`、`tdd`、`simplify`、`code-review` 这些 Engineering Discipline 按实际问题叠加。长任务则依靠 `MAP.md`、`SPEC.md`、tickets 和 evidence 之类的 artifact 保存事实，不把所有状态都压在一条聊天记录里。

## 三：我是怎么学习 Agent 的

[Agent 学习篇](/ai-coding-workflow-3/) 记录的是另一条线：这些概念我是怎么慢慢补起来的。

我的学习方式一直比较工程化。先在项目里遇到问题，再去找对应机制。Agent 忘了前文，才认真研究 Context 和 Memory；长任务会中断，才去理解 Runtime、Goal 和 Harness；多个 Agent 一起得出错误结论，才开始关心 context isolation 和 independent review。

最后串起来的大概是 Model、Context、Tool、Harness、Runtime、Skills、Memory、多 Agent 和 Automation。这个顺序不是课程大纲，只是我实际踩坑以后形成的理解路径。

## 四：长期使用以后留下的一些判断

[感悟篇](/ai-coding-workflow-4/) 不再讲具体工具，主要保留这一年反复验证过、目前仍然认可的一些判断。

比如 Context 往往比 Prompt 技巧更值得先检查；Runtime 和工程环境会直接影响模型能力能不能稳定发挥；多 Agent 的价值更多来自独立性；Automation 适合边界稳定、结果可检查的工作；Agent 的自我汇报不能替代真实证据。

还有一个感受越来越明显：**代码生成越快，人的判断越需要慎重。**

AI 把实现速度抬高以后，需求是否值得做、改动边界是否合理、证据是否充分、维护成本是否接受，这些判断并没有一起自动变简单。

## 这次梳理对我自己的价值

写这组文章之前，我脑子里其实已经有一套工作习惯，只是很多东西散落在 AGENTS.md、Skills、自动化任务和日常对话里。把它们写出来以后，哪些属于长期原则、哪些只是当前工具的能力、哪些已经设计过度，就清楚了很多。

我现在会更频繁地问几个很实际的问题：当前最大的未知是什么？这个任务真的需要 Skill 吗？哪些信息值得写进 artifact？Runtime 已经负责的事情，还要不要再造一层控制？最后拿什么证据判断任务完成？

这四篇就是目前的答案。以后工具和做法继续变化，我大概率还会改，但也正因为会改，才值得偶尔把当前状态写下来。
