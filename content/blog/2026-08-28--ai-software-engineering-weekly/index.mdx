这周的更新主要落在两个方向：Cloud Agent 开始接触仓库、事件和协作入口；Claude Code 继续补跨会话通信、受限执行和长任务能力。研究侧，SWE-bench Science 说明公开榜单在专业工程场景里的解释力仍然有限。

## 官方更新

### Cursor：仓库、事件和 Cloud Agent 开始绑得更紧

Cursor 最近几次更新可以合在一起看。8 月 17 日推出 [Origin Code Hosting](https://cursor.com/changelog/origin-code-hosting)，把 repo、PR、代码浏览和 Agent 放到同一个产品里；8 月 19 日的 [Cloud Agents and Cursor Harness Improvements](https://cursor.com/changelog/08-19-26) 加入事件订阅、`/goal`、独立 VM 上运行的 subagent，以及长任务中的 steering；8 月 27 日又上线 [Start from scratch, without a repo](https://cursor.com/changelog/start-from-scratch)，用户甚至可以先启动 Cloud Agent，再决定是否把结果保存成 Origin repo。

三次更新合在一起，Cursor 的产品方向比较清楚：尽量把 Agent 完成任务所需的环境收进同一套产品，减少在 IDE、GitHub、CI 和聊天工具之间来回切换。

Origin 对从 GitHub 同步进来的仓库明确保留 GitHub 作为 source of truth，但 Cursor 自己托管的 repo、Cloud Agent session、PR 和事件订阅也开始承载更多状态。状态分散到这些位置之后，故障恢复和审计会越来越依赖平台自己的状态模型。集成体验更顺，同时也会把“哪些状态放在哪里”变成架构问题。

### GitHub Copilot：Agent 入口进了 Teams

GitHub 在 [Shared agentic work with GitHub Copilot in Microsoft Teams](https://github.blog/changelog/2026-08-21-shared-agentic-work-with-github-copilot-in-microsoft-teams/) 里把 Copilot cloud agent 带进了 Teams。频道、线程和私聊都可以启动共享 Agent session；有仓库写权限的人还能让 Copilot 直接修改代码。

入口本身不复杂，麻烦在任务归属。一次开发任务可能从 Teams 讨论开始，随后进入 Agent session，产生 commit 和 PR，再被 CI 或 review 重新唤醒。没有稳定的 task identity 时，日志虽然能查到，任务却不一定能完整还原。

### Claude Code 2.1.248：协作扩展，同时增加受限执行

[Claude Code v2.1.248](https://github.com/anthropics/claude-code/releases/tag/v2.1.248) 增加了 `--restricted`，会移除默认可执行命令或代码的内置工具，并限制 `WebFetch`、文件访问和权限绕过。同一版本还扩大了 `SendMessage` / `ListAgents` 的跨会话通信范围，让 `/loop` 的动态模式在 Bedrock、Vertex、Foundry 等环境中也可用，并修了不少 background session、worktree lock、prompt cache 和跨会话消息相关的问题。

跨会话通信和 `/loop` 让任务更容易持续运行，`--restricted` 以及 background/worktree 相关修复则把执行边界收得更细。长任务和多会话协作进入真实项目后，权限、隔离、恢复这些问题会很快超过“多开几个 subagent”本身。

过去在 CLI Agent 上常见的取舍，是完全开放工具，或者频繁人工确认。`--restricted` 给了更细的运行时配置，但它仍然只是 Claude Code 自身的一套策略，不能替代容器权限、仓库权限、网络策略和 CI 里的独立验证。

### OpenAI：`codex mcp-server` 退场，Agent runtime 接口继续分化

OpenAI 8 月 24 日在 [Release Notes](https://openai.com/products/release-notes/) 中宣布弃用 `codex mcp-server`，推荐改用 Codex app server；如果要从 Claude Code 使用 Codex，则推荐 Codex plugin for Claude Code。

这项变更可以看作接口分层的一次调整。MCP 适合工具发现和调用，一个完整 Coding Agent 还要处理 session、审批、状态、事件和流式执行结果。把整套 Agent runtime 都包装成 MCP tool，接口很容易变得别扭。

目前官方只说明了迁移方向，不能据此推断 app server 会成为通用 Agent runtime 标准。内部平台如果也在做类似集成，把工具协议和任务运行时分开建模会更稳妥。

## 研究与 Benchmark

### SWE-bench Science：专业领域仍然会把 Coding Agent 拉回现实

8 月 20 日发布的 [SWE-bench Science](https://arxiv.org/abs/2608.19799) 收集了 98 个 GitHub 仓库中的 119 个科学软件工程任务，覆盖 20 个科学领域。论文报告中，表现最好的 Agent 在 pass@1 上仍低于 50%。作者归纳的常见失败包括领域知识不足、探索方向错误、修复覆盖不完整，以及无法把已有科学知识正确泛化到新情况。

论文的配对消融还有一个结果：质量高、和任务匹配的科学指导会改善平均表现和 token 效率；不合适的指导可能产生锚定，未必提高精确修复成功率。这给“多塞一些上下文总会更好”泼了点冷水。

这和项目里的 `AGENTS.md`、Skills、Rules 很接近。上下文工程难维护的地方之一，是规则的适用范围和信噪比。规则长期只加不删，和当前任务无关的内容会越来越多，旧经验也可能干扰新任务。

这也限制了统一 Coding Agent 排名的解释力。仓库级修复能力会被领域知识、验证方式、环境复杂度和探索策略明显影响。评估实际 workflow 时，一套来自真实项目的任务集往往比单看公开榜单更有参考价值。

## 社区观察

### Claude Code 的跨会话通信已经可用，但可靠性还在磨

Claude Code 正在持续扩展跨会话协作，不过 GitHub Issues 里已经出现多组相似反馈。比如 Windows 用户报告过 [消息显示在目标 session 但没有真正进入模型队列](https://github.com/anthropics/claude-code/issues/86671)，也有人遇到 [Windows Desktop 中 SendMessage 显示成功但实际没有送达](https://github.com/anthropics/claude-code/issues/87615)。这些都是用户报告，不能据此判断所有平台都存在同样问题。

这类失败的麻烦在于系统可能没有明确报错：界面显示投递成功，任务却没有继续。一旦跨 session 消息进入自动化编排，delivery acknowledgement、timeout 和可查询状态就成了基础设施要求，单靠一次 `SendMessage` 的成功返回不够。

目前这套能力更适合作为实验性协作机制，还不宜直接当成内部消息总线。

## 总结

这周几项产品更新都在扩展 Agent 的运行范围：Cursor 把仓库、事件和 Cloud Agent 绑得更紧，GitHub 把 Copilot session 放进 Teams，Claude Code 则补了跨会话协作和受限执行。跨工具、跨会话之后，状态能不能追踪、验证是否独立，比入口本身更值得关注。

SWE-bench Science 给出的信号更朴素：专业工程任务仍然依赖领域知识和上下文质量。项目里的 `AGENTS.md`、Skills、Rules 需要定期清理，也要用真实任务集验证这些规则到底有没有帮忙。
